# OneStop Auth0 implementation plan

> **For agentic workers:** Use superpowers:executing-plans to implement this small change in the existing application. Checkboxes track implementation, not completed work.

**Goal:** Add real email/password sign-up, login, logout and an account menu quickly, without requiring an application database.

**Architecture:** Auth0 Universal Login owns credential collection and the user directory. The existing Express server uses Auth0's `express-openid-connect` SDK for the authorization-code callback and encrypted cookie session; React reads a small same-origin session endpoint. Housing research remains shared, while browser-saved preferences and shortlists are separated by account.

**Tech Stack:** Existing Express 5, React 19, TypeScript, Vite, Vitest and Playwright; add `express-openid-connect`. No Next.js migration, MongoDB or second authentication SDK.

**Spec:** The scope and acceptance contract below records the proposed fast implementation. The user requested rapid Auth0/account integration and asked whether a database is needed; the database-free recommendation is not a claim that cross-device persistence was declined.

## Global constraints

- Preserve OneStop's working CMU demo, evidence, utility distinctions, routing and comparisons.
- Preserve the user's existing uncommitted branding and product-direction edits.
- No app-managed password collection or storage. The user enters passwords directly into Auth0.
- Keep application secrets server-side in ignored `.env.local`; never prefix them with `VITE_`, commit them, or print them in verification output.
- Use the server-validated Auth0 `sub` as identity; email is display data, not an authorization key.
- Browser-storage separation prevents accidental account mixing; it is not a privacy boundary against someone with access to the browser or its developer tools.
- A real provider roundtrip is required before reporting login as working. Fixtures and mocked sessions cannot establish that.
- Estimated implementation and verification: 45–90 minutes after provider access/configuration is available. This is an estimate, excluding user login/MFA/email delays and public deployment.

## Scope and acceptance contract

The recommended first version has three deliverables:

1. **Real accounts:** Auth0-hosted email/password sign-up and sign-in, a persistent session, logout, and an account menu showing the signed-in email/name. Password reset uses Auth0's hosted flow.
2. **Honest persistence:** Shortlists and criteria are saved on this browser under the current identity. Label them “Saved on this browser.” Guest work stays separate; no automatic attribution of an earlier user's data to the next login. Guest CMU research remains usable.
3. **Verified demo:** Sign up/login, reload, log out, switch identity, and confirm the original housing decision flow still works at `http://127.0.0.1:4173`.

An application database is unnecessary for these accounts: Auth0 supplies its own user store. To make searches and shortlists follow a user across browsers/devices, add server-side persistence as a separate deliverable. MongoDB is one option, alongside PostgreSQL or SQLite on an appropriate persistent server. Store housing workspace data keyed by authenticated identity there; continue keeping passwords in Auth0.

Existing snapshots, source imports and research jobs are shared local-demo resources. This addition does not turn them into private per-user research or deploy the local server publicly. `/api/account` will require an authenticated session; public housing endpoints retain their existing behavior.

## Provider setup

Current state: the user is unsure whether they have an Auth0 account. The Auth0 dashboard was opened for them. No tenant credentials or application settings have been obtained, and no auth code is implemented.

The user signs in or registers at [the Auth0 dashboard](https://manage.auth0.com/). Their dashboard administrator login is separate from an end-user account created through OneStop's login page. Select/create a tenant, then create a **Regular Web Application** named **OneStop** and enable its Auth0 email/password database connection and sign-up.

Configure these exact URLs:

| Setting | Local production demo | Vite development |
| --- | --- | --- |
| Application origin | `http://127.0.0.1:4173` | `http://127.0.0.1:5173` |
| Allowed callback | `http://127.0.0.1:4173/auth/callback` | `http://127.0.0.1:5173/auth/callback` |
| Allowed logout return | `http://127.0.0.1:4173` | `http://127.0.0.1:5173` |

Use the domain, client ID and client secret from this application. Generate a separate random session secret locally. `.env.local` holds `AUTH0_ENABLED`, `AUTH0_ISSUER_BASE_URL`, `AUTH0_CLIENT_ID`, `AUTH0_CLIENT_SECRET`, `AUTH0_SECRET`, and `AUTH0_BASE_URL`. The base URL must match the browser origin in the current run, not the internal API port 4318. No wildcard callback or user-supplied return destination.

Session contract:

```ts
export type AuthUser = {
  sub: string;
  name?: string;
  email?: string;
  emailVerified: boolean;
};
export type SessionState =
  | { status: 'disabled' }
  | { status: 'anonymous' }
  | { status: 'authenticated'; user: AuthUser };
// GET /api/session: 200 SessionState, Cache-Control: no-store.
// GET /api/account: 200 { user: AuthUser }, or 401 JSON when anonymous.
// Client-only loading/error states must not be treated as a resolved identity.
```

## Task 1: Working server authentication

- [ ] Add configuration and API tests in `tests/api/auth.test.ts` using the existing HTTP-server test pattern. Check disabled configuration, invalid partial configuration, anonymous session state, JSON 401 for `/api/account`, and rejection of a forged session cookie. Check an invalid callback cannot create a session.
- [ ] Add the SDK dependency and load `.env.local` through Node's `loadEnvFile` when present, before reading configuration. Keep environment variables supplied by the runner authoritative. Document required values in `.env.example` without real credentials.
- [ ] Implement `readAuthConfig(env: NodeJS.ProcessEnv): ConfigParams | null` and `mountAuth(app: Express, config: ConfigParams | null): void` in `server/auth.ts`. Explicitly disabled/missing configuration keeps guest demo operation available. Enabling auth with incomplete configuration fails startup with missing variable names only.
- [ ] Use the following SDK configuration core, mapping each field from the validated server environment:

```ts
const config = {
  authRequired: false,
  issuerBaseURL: env.AUTH0_ISSUER_BASE_URL,
  baseURL: env.AUTH0_BASE_URL,
  clientID: env.AUTH0_CLIENT_ID,
  clientSecret: env.AUTH0_CLIENT_SECRET,
  secret: env.AUTH0_SECRET,
  authorizationParams: {
    response_type: 'code',
    response_mode: 'query',
    scope: 'openid profile email',
  },
  routes: {
    login: false,
    callback: '/auth/callback',
    logout: '/auth/logout',
  },
  auth0Logout: true,
};
```

- [ ] Mount the SDK before the existing mutation-origin guard and SPA catch-all. The explicit GET query callback avoids the current guard rejecting an Auth0 form POST. Preserve the SDK's state/nonce and cookie protections; use HTTPS-only secure cookies when the configured origin is HTTPS.
- [ ] Register `/auth/login` and `/auth/signup` using `response.oidc.login`, fixed `returnTo: '/'`, and `screen_hint: 'signup'` for sign-up. Refuse arbitrary return URLs. SDK logout clears the app session and returns through the configured Auth0 logout flow.
- [ ] Implement the session contract from `request.oidc.isAuthenticated()` and validated profile claims. Return only the declared profile fields, never tokens. For an unauthenticated `/api/account` request, return JSON 401 rather than redirecting a fetch to HTML.
- [ ] Handle login denial/callback failure with a generic recoverable message and a route back to the demo. Do not expose provider error descriptions, codes, tokens or stack traces in the UI/logs.
- [ ] Proxy `/auth` to `http://127.0.0.1:4318` alongside `/api` in Vite. Run the focused auth API tests and verify login redirects carry the intended callback URL and code flow.

## Task 2: Account control and browser-saved work

- [ ] Introduce `src/lib/auth.ts` with the declared `SessionState` contract. Retrieve `/api/session` before choosing a persistence identity. A request failure is a recoverable account-loading error, not evidence that the user is a guest.
- [ ] Extract the existing `Stored` parsing/persistence into `src/lib/storage.ts`; preserve existing schema validation and malformed-storage recovery. Use an explicit helper:

```ts
export function workspaceStorageKey(sub: string | null): string {
  return sub === null
    ? 'onestop-search-v2:guest'
    : `onestop-search-v2:account:${encodeURIComponent(sub)}`;
}
```

- [ ] Add regression coverage proving guest/user A/user B workspaces differ, a switch restores the destination identity before any write, failed session retrieval cannot overwrite guest work, and reset clears only the current workspace. Migrate the legacy `address-search-v1` value to the guest workspace once; never automatically import it into an account.
- [ ] Gate persistence on completed identity resolution and state restoration. On login/logout use full navigation so the application starts from a fresh identity. Recheck identity when an existing tab regains focus, cancelling stale restoration and blocking writes during a switch. Keep account-scoped local data on logout so a later login in this browser can restore it.
- [ ] Add `AccountMenu` to the existing header: Sign in/Create account for a configured anonymous session; name/email and Log out when authenticated. Do not show a working-login claim when auth is disabled. Include “Saved on this browser”; only label an email verified when `emailVerified` is true. Use current typography, color tokens and restrained spacing, keyboard access, and an accessible menu label.
- [ ] Preserve the selected CMU criteria, map/list controls, evidence, comparisons and demo reset. An account-loading failure can leave the public demo usable without persisting uncertain-identity changes.

## Task 3: Provider verification and handoff

- [ ] Configure the actual Auth0 application and ignored local secrets, then build with `npm run build`. Run `npm test` once; repair failures caused by this change before browser verification.
- [ ] Verify at port 4173 with a real Auth0 end-user: hosted sign-up/login → callback → signed-in menu → reload retains session → logout removes account access. The user supplies their password directly to Auth0 and completes any verification email themselves. Record verification as pending if the provider roundtrip cannot be completed.
- [ ] Verify saved criteria/shortlist remain associated with that account in this browser and are absent for a guest or a different test identity. Use two authorized demo accounts when available; deterministic storage tests cover separation until a real second identity is available.
- [ ] Check invalid/expired session behavior and denied login recovery. Browser automation may mock account states for UI tests only; distinguish those results from live Auth0 evidence.
- [ ] Re-run the existing production decision-flow browser tests. Inspect the header and account menu at desktop and mobile widths for overflow, keyboard reachability and visual consistency. Do not start another broad design cycle.
- [ ] Rebuild/restart the existing server only after recording its current process identity and successful checks. Confirm `/api/health`, `/api/session` and the populated OneStop page, then document startup and verified provider behavior in the runbook/verification record.

## Optional next increment: MongoDB-backed saved work

If the user wants cross-device persistence now, budget approximately 1–2 additional hours after database access is available, subject to integration findings. Add a `workspaces` collection with a unique identity key, validated criteria/shortlist content, a revision and update time. Read/write endpoints derive ownership exclusively from the authenticated session. Test user A cannot read or overwrite user B, stale saves produce a conflict, and network failures preserve the local draft. This requires explicit UI sync status and an opt-in import of existing browser work; it does not justify moving passwords into MongoDB or claiming shared research jobs are now private.
