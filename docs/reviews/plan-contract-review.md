# Plan and contract review

Scope: independent pre-build review of `PROJECT.md`, C01–C22, the design, and `CONTRACTS.md`. The final build go has not been given; this is not authorization for application code.

## Must fix before build

1. **A completed discovery or routing job cannot deliver its new snapshot to the client.** `POST /api/discovery` and `/api/routes` return only a `Job`; `GET /api/jobs/:id` returns only that job. `Job.snapshotId` identifies a result, but the API has no `GET /api/snapshots/:id`, no current-snapshot endpoint, and no snapshot in the terminal job response. The specified UI therefore cannot atomically replace its view, render a refresh diff, or use new route facts. Add one canonical read path (prefer `GET /api/snapshots/:id`, with the terminal job retaining `snapshotId`) and specify: publication order, 404/409 behavior, response snapshot validation, and client reconciliation of favorites/selection. Use it for both job types.

2. **Timing and amenity criteria are typed as editable hard filters but have no evaluable data or rules.** `moveIn`, `leaseMonths`, and amenity arrays appear in `Criteria`/`CriteriaPatch`; `Home.availability` and `leaseTerms` are only free-text `Fact<string>`, and amenity keys are unconstrained. This permits contradictory implementations: unknown timing might silently pass, a prose date might be compared as a string, or a flexible user requirement could accidentally exclude inventory. For the morning build, make timing and lease display/readiness-only and remove them from active patches/alternative generation. If editable filtering is required, first define normalized availability/lease and canonical amenity identifiers plus pass/fail/unknown semantics and boundary tests.

3. **The contract needs an explicit matching table and validation invariants.** The design says exactly 2 bedrooms, 2+ advertised bathrooms, whole-home monthly base rent, and a current, valid route; the types alone do not force those rules. Add a concise contract table and tests: bedrooms use equality; bathrooms use `>=`; only `whole_unit` + `month` + `base_rent` can calculate the personal rent filter; ranges/from/effective/unknown quotes are leads or unknown unless a defensible bound is specified; route must be `ok`, current destination version, and no >75 m snap. Also define cost behavior for required whole-household charges (allocated by the selected split), per-person charges, and unknown required fees. This preserves the crucial distinction: unknown utilities/fees make costs incomplete and questions visible, but unknown utilities do not fail a rent-only match.

4. **Evidence provenance is described but not enforceable at the schema boundary.** A `Fact` can claim `sourced` with no evidence IDs, cite nonexistent IDs, or attach a fact to a building-wide capture while the home represents a unit. Require `validateSnapshot` to enforce state/value/evidence consistency, unique IDs, referential integrity, source-run/source-entry links, and compatible evidence scope for every hard listing fact. Define the permitted relationship between `Home.scope`/`offerKey` and `Evidence.scopeKey`; reject incompatible multi-unit combinations. This is the specific safeguard against repeating the known 1BR/2BR date mix-up.

5. **“Whole-city discovery” has no concrete coverage contract.** `SourceRun.bounds` and `queryDescription` are opaque strings, so the UI cannot truthfully explain what was searched, what a widened destination/criteria change reuses, or why `discoveryNeeded` is true. Add a small structured `ResearchScope` to snapshot/run metadata (market/neighborhood query areas, layout/price query intent, destination version, checked-at) and a deterministic `needsDiscovery(criteria, scope)` rule. It need not promise exhaustive coverage; it must make the existing inventory's limits inspectable and force an honest empty/research-needed state after a material market or destination change.

6. **The five-hour, three-worker plan must have a hard feasibility gate.** The design currently combines real three-organization seed collection, a bounded model worker, adapters/extraction/quarantine/deduplication, 8 routes, GTFS/OSM enrichment, API/jobs, a responsive comparison UI, and reviews. That is beyond a safe parallel build unless the plan timeboxes the first dependency. First run a source/seed spike; by its deadline either produce 12 addressed records across 3 organizations with the required evidence/route subset, or narrow live discovery to proven CMU/manager pages and visibly retain the other sources as surveyed/link-only gaps. Do not substitute fabricated records. Assign one integration owner for contracts/snapshot publication, reserve a browser/provenance review after the rendered core and again for the candidate, and name a repair owner per finding.

## Optional after the above

- Add a snapshot diff payload sufficient to distinguish changed facts from merely not re-observed homes, so coverage and stale labels remain defensible.
