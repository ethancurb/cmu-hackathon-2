## A five-minute sponsor decision

For at most one initial sponsor candidate, record:

1. **User job:** the concrete behavior the integration enables.
2. **Counterfactual:** what useful outcome disappears if it is removed.
3. **Evidence:** an actual successful request or service operation using the account/runtime intended for the demo.
4. **Full cost:** setup, credentials, SDK, latency, deployment, testing, and explanation time.
5. **Entry requirement:** exact organizer wording, link, and form selection, separating confirmed details from unknowns.
6. **What it replaces:** the feature or work dropped to fit it into the remaining time.

If the integration does not improve the same core experience, omit it. Add another sponsor only after the working candidate and submission path are secure. Do not pursue a second product inside a sponsor entry.

## Evidence to keep with an actual entry

Record the service and feature used, code path, one sanitized successful result, its visible user effect, the chosen submission field, and any disclosure requested by the organizer. These are useful preparation items, not a claim that organizers require this exact checklist.

Do not turn speculative scale estimates, query complexity, or a future adapter into technical claims. Measure the relevant behavior on the actual tier and deployment. The [prior-project lessons](../strategy/LESSONS.md) explain why appealing architecture prose can outpace verified capability.
